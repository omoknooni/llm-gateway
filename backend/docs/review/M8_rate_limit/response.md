## P1-1 tree 가 다른 모델 설정을 해석 후보에 넣음 — 수용, 수정

지적이 정확합니다. `tree()` 가 `list_configs(scope=TEAM, scope_id=...)` 로 **모든 모델 차원의
행**을 가져와 그대로 `policy.resolve()` 에 넘겼습니다. 해석은 같은 scope 안에서 `model_scoped`
를 더 구체적으로 치므로, 모델 미지정 조회에서도 `claude-x` 전용 50 이 팀 전체 600 을 덮습니다.

영향은 두 가지였습니다.

- 화면이 "이 팀의 기본 한도는 50" 이라고 잘못 말합니다.
- `team_resolution` 을 기준으로 삼는 **상위 초과 배지**가 그 잘못된 값으로 판정됩니다.
  정상 설정(500 ≤ 600)에 초과 배지가 붙습니다.

`RateLimitRepository.list_for_subject` 는 이미 SQL 에서 같은 규칙으로 거르고 있었는데,
`tree` 만 `list_configs` 를 쓰면서 그 규칙을 잃었습니다. 규칙을 한 곳에 모으려고
`_for_dimension()` 헬퍼로 뽑아 팀·멤버 설정 양쪽에 적용했습니다.

회귀 테스트 3건을 넣었습니다 — 모델 미지정 조회가 전체 한도를 쓰는 것, 모델 지정 조회가
그 모델 한도를 쓰는 것, 배지가 같은 차원으로 판정되는 것.

## P1-2 effective 의 (user_id, virtual_key_id) 조합 미검증 — 수용, 수정

지적대로입니다. `user_id or key.owner_id` 로 사용자 축을 정하고 나서
`_require_can_view(actor, resolved_user, ...)` 를 불렀는데, 이 판정은
`actor.user_id == user_id` 에서 **먼저 통과**합니다. 자기 id 를 넣으면 키의 팀을 보지 않고
지나갑니다. 같은 팀 일반 사용자뿐 아니라 다른 팀 키도 열립니다.

정확성 문제도 함께 있습니다. 실재하지 않는 (사용자, 키) 조합의 계층을 계산하면, 화면의
한도가 그 키로 요청했을 때 실제 집행되는 값과 달라집니다.

두 가지를 고쳤습니다.

1. 사용자 축은 **키가 말하는 소유자**로만 정합니다. 호출자가 준 `user_id` 가 실제 소유자와
   다르면 400 `subject_mismatch` 로 거절합니다.
2. 인가를 `_require_can_view_key()` 로 분리했습니다. 소유권을 호출자가 보낸 id 가 아니라
   키의 소유자와 비교합니다. `TEAM` 소유 키는 사람에 귀속되지 않으므로 ADMIN 과 그 팀
   팀장만 봅니다.

회귀 테스트 3건 — 조합 불일치 거절, 침입자가 자기 id 를 섞어도 막히는 것(그리고 `user_id`
를 빼도 막히는 것), 소유자 본인은 정상 조회되는 것.

## P2 팀장의 목록 조회에서 scope_id 미적용 — 수용, 수정

`list_limits` 의 비 ADMIN 분기가 `list_configs(scope=..., model_alias=...)` 만 넘기고
`scope_id` 를 떨어뜨렸습니다. 권한 범위로 걸러지긴 하지만 요청한 필터가 무시되므로,
한 멤버를 지정해도 팀 전체 설정이 돌아옵니다.

필터를 그대로 넘기도록 고쳤고, **권한 밖 대상을 지정하면 빈 목록이 아니라 403** 으로
바꿨습니다. 빈 목록이면 "설정이 없다"와 "볼 수 없다"를 구분할 수 없습니다(00 문서 원칙).

회귀 테스트 2건 — 지정한 멤버만 돌아오는 것, 다른 팀 멤버 지정이 403 인 것.

## 남은 것

gateway 의 집행 카운터 키 최종 형태(윈도 표기, cluster mode 해시태그)가 Phase 4 미확정이라
키를 만들 수 없습니다. 확정되면 `RateLimitService.usage()` 한 곳에서 읽습니다.
