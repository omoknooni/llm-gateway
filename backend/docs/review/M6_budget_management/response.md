## P1-1 동시 갱신 시 배분 합계 초과 — 수용, 수정

지적이 정확합니다. 검증이 **읽는 행과 쓰는 행이 달라서**(팀 한도·기존 배분을 읽고 다른
사용자의 행을 INSERT) 행 잠금으로는 막히지 않는 write skew 입니다. 팀 예산이 아직 없으면
잠글 행 자체가 없다는 지적도 그대로입니다.

권장안 1의 두 번째 갈래(팀 id advisory lock)를 택했습니다. `SELECT ... FOR UPDATE` 로는
"팀 예산 행이 없는 상태"의 경쟁을 막지 못해, 두 방식을 섞으면 규약이 둘이 됩니다.

- `app/core/locks.py` 의 `lock_team_budget()` — `pg_advisory_xact_lock(ns, crc32(team_id))`.
  **트랜잭션 스코프**라 커밋·롤백에 자동으로 풀립니다. 해제를 잊을 수 없는 형태를 택했습니다.
- 적용: 팀 예산 설정, 사용자 예산 설정(소속 팀), 배분 일괄 설정.
- **해제 경로에는 걸지 않았습니다.** 제약을 없애거나 합계를 줄이는 방향이라 불변식을 깰 수
  없습니다. 이 판단을 코드 주석과 05 문서 표에 남겼습니다.
- `jobs/locks.py` 를 `core/locks.py` 로 옮겼습니다. 서비스가 `app.jobs.*` 를 import 하는
  것은 계층 역전입니다.

권장안 3(동시 요청 통합 테스트)은 **하지 못했습니다.** 개발 환경에 PostgreSQL 이 없어
통합 테스트 자체가 아직 한 건도 없습니다. 대신 잠금이 트랜잭션 스코프로 걸리는지를 단위
테스트로 고정했습니다(`test_team_budget_lock_is_transaction_scoped`). DB 가 붙는 시점의
통합 테스트 목록에 남겨 둡니다.

## P1-2 4자리 초과 금액 — 수용, 수정

권장안 1 그대로 적용했습니다. `limit_usd`(설정·배분)와 `used_usd`(재시드)에
`max_digits=14`, `decimal_places=4` 를 걸어 DB 표현 범위를 벗어난 입력을 422 로 거절합니다.

권장안 2(명시적 반올림 규칙)는 **택하지 않았습니다.** 반올림 규칙을 정하면 "사용자가 보낸
값과 저장된 값이 다른" 상태를 정상으로 만듭니다. 금액에서는 표현할 수 없는 값을 조용히
바꾸는 것보다 거절하는 편이 낫습니다. 거절이 기본이면 `counter_value()` 의 `quantize()` 는
이미 4자리인 값에 대한 형식 정규화로만 남습니다.

권장안 3의 DB 통합 테스트는 P1-1 과 같은 이유로 못 했고, 경계값 스키마 테스트는
추가했습니다(`0.00005`, `1.23456`, 정수부 초과, 그리고 경계인 `1234567890.1234`).

## P1-3 Redis 쓰기 실패 후 자동 복구 없음 — 수용, 다른 방법으로 수정

지적한 상태("응답은 200, 항목만 `counter_updated: false`, 재시도 없음")가 실제로 있었고,
**집행이 옛 값을 계속 쓰는 상태가 조용히 남는** 것이 문제의 핵심이라는 진단에 동의합니다.

권장안 1(outbox + 재시도 job)은 택하지 않았습니다. 근거는 두 가지입니다.

- 기존 재시도 기반(`audit.cache_invalidation_failures` + `retry_failed`)은 **DEL 전용**입니다.
  재시드는 값을 SET 해야 해서 재사용하면 카운터를 지우게 됩니다 — 소진액이 0 으로 리셋되는
  가장 나쁜 실패입니다. 그래서 새 테이블이 필요한데, 재시드는 사람이 부르는 복구 도구라
  "실패하면 다시 부르면 되는" 연산입니다. 재시도 인프라를 새로 만들 만한 빈도가 아닙니다.
- 두 저장소에 걸친 갱신은 원자적으로 만들 수 없습니다. 고를 수 있는 것은 **실패했을 때
  어느 쪽이 남는가** 뿐입니다.

대신 순서를 바꿔 실패를 **조용하지 않게** 만들었습니다.

1. DB 변경을 트랜잭션에 쌓습니다(커밋하지 않음).
2. 카운터 전체를 **파이프라인(MULTI/EXEC) 한 번**으로 씁니다. 실패하면 롤백하고 503
   `counter_write_failed` 로 거절합니다 — 아무것도 바뀌지 않습니다. 항목별로 나눠 쓰지
   않는 이유는 일부만 바뀐 상태가 재시드로 고치려던 상태보다 나쁘기 때문입니다.
3. 커밋합니다.

남는 창은 3번 실패입니다. 이때는 카운터만 새 값으로 남는데, **집행은 운영자가 의도한 값을
쓰게 되고** 어긋난 내구 사본은 기존 `verify_budget_counters` job 이 drift 로 잡아냅니다.
원래 순서(커밋 먼저)의 잔여 상태와 정확히 반대이고, 이쪽이 덜 나쁩니다.

이에 따라 응답에서 `counter_updated` 를 제거했습니다. 항목별 부분 성공이 더 이상 존재하지
않으므로, 남겨 두면 항상 `true` 인 필드가 "확인해야 할 것"처럼 보입니다.

권장안 2(부분 실패 경보)는 부분 실패 자체를 없애 해소했고, 권장안 3(복구 통합 테스트)은
DB·Redis 가 붙는 시점으로 남깁니다. 파이프라인 사용과 실패 전파는 단위 테스트로
고정했습니다.

## 검증

리뷰의 "검증 범위" 지적(통합 테스트 부재)도 해소했습니다. `backend/docker-compose.test.yml`
로 PostgreSQL·Redis 를 띄우고 돌립니다(`./scripts/test-stack.sh up && ./scripts/test-stack.sh test`).

- `ruff check` 통과, 전체 212개 통과 (단위 182 + 통합 30)
- 리뷰가 요청한 세 건이 모두 통합 테스트로 들어왔습니다.

| 리뷰 권장 | 테스트 |
|---|---|
| P1-1 동시 요청 합계 (권장안 3) | `test_budget_concurrency.py::test_concurrent_user_budgets_cannot_exceed_team_limit` / `::test_concurrent_allocation_replacements_keep_invariant` |
| P1-2 경계값 DB·Redis 일치 (권장안 3) | `test_budget_reseed.py::test_db_value_and_redis_counter_agree` (5개 경계값) |
| P1-3 Redis 장애 후 복구 (권장안 3) | `test_budget_reseed.py::test_reseed_rolls_back_when_counter_write_fails` / `::test_reseed_succeeds_after_redis_recovers` |
| M2 미검증 항목 | `test_schema_and_grants.py` (8건) |

**동시성 테스트가 실제로 버그를 잡는지 확인했습니다.** `lock_team_budget()` 을 임시로
무력화하고 돌리면 두 테스트가 실패하고 배분 합계가 180 이 됩니다. 잠금을 되살리면 통과합니다.
리뷰가 지적한 write skew 가 재현되고, 수정이 그것을 막는다는 뜻입니다.

## 통합 테스트를 붙이면서 드러난 것

`db/init/02_create_roles.sql` 이 **한 번도 동작한 적이 없었습니다.** psql 변수(`:'name'`)가
dollar-quoted 블록(`DO $$ ... $$`) 안에서 치환되지 않아 문법 오류로 끝납니다. 오프라인 SQL
렌더링으로는 드러나지 않는 결함이고, 스크립트를 실제로 돌린 이번에 처음 나왔습니다.
`\gexec` 로 고쳤고 함정을 `db/README.md` 규칙에 남겼습니다.

## 남은 것

- 라우터 계층(HTTP) 통합 테스트는 아직 없습니다. 현재 통합 테스트는 서비스·job·스키마 층입니다.
  인가 분기(403/404)가 의존성·서비스 양쪽에 걸쳐 있어 HTTP 레벨 확인이 있으면 좋습니다.
- M7 집계의 **실데이터** 검증은 gateway 가 이벤트를 쓰기 시작해야 합니다. 지금은 테스트가
  직접 넣은 이벤트로 확인했습니다.
